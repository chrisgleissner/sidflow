# Migration addendum: the full SQLite export

An addendum to [Migrating from the 0.5-era data release to 0.8.0](./0.5-to-0.8.md), for
consumers of the **full** `sidcorr-1` SQLite export — `u64deck` in particular.

Everything in the main guide applies to you as well. This page exists because the full
export is the profile that changed most between these releases, and because most of that
change is in parts of the file a consumer may or may not use. Whether this migration is a
one-line configuration change or something worth an afternoon depends entirely on which
columns you read, so the sections below are organised around that question.

---

## What the full export is, and what changed inside it

The `sidcorr-1` SQLite file has three tables. `meta` holds the manifest. `tracks` holds one
row per playable subsong, with its ratings, its similarity vector, and the complete raw
feature record the classifier produced. `neighbors` holds precomputed nearest-neighbour
rows.

Between the 0.5-era release and 0.8.0, the `tracks` table gained a much larger similarity
vector, and the `neighbors` table went from empty to holding 2.2 million rows. Those two
changes account for essentially the whole size increase. The raw feature records — the
`features_json` column — are structurally unchanged: 58 keys were added between feature
schema 1.3.0 and 1.5.0, and none were removed.

That distinction matters, because it means a consumer that reads only `features_json` is
paying for two things it may not be using.

---

## The file got bigger, and there are now two smaller options

The plain SQLite download went from **416 MB to 982 MB**. After import, a compact database
built with `slim_database()` holds **269.4 MB**, where the 0.5-era export produced 37.6 MB.

The reason is worth understanding rather than just absorbing, because it points at which of
the smaller options will suit you.

**The similarity vector went from 4 dimensions to 58.** In the 0.5-era release each track's
`vector_json` was a 4-element array derived from its `e`/`m`/`c`/`p` ratings. It is now a
58-dimension description: 24 perceptual dimensions from the rendered audio, 11 describing
pitch and texture, and 23 derived from the SID register-write trace — that is, from what
the tune's playroutine does to the chip rather than from how it sounds. Stored as JSON text
at full precision, that is roughly 1.1 KB per track, or about 98 MB across the corpus.

**The `neighbors` table went from 0 rows to 2,196,700.** The 0.5-era export shipped with no
precomputed neighbours at all. It now stores the top 25 neighbours of every track. Each row
repeats two full text track IDs, so the table occupies around 258 MB in the file and
roughly 232 MB of a compact database built from it.

Two new assets were added in 0.8.0 to give consumers a way around that. Neither replaces
anything: **no existing asset was renamed or removed**, and all four original filenames
still resolve from `releases/latest/download/`.

### The gzipped full export — 194 MB

`sidcorr-hvsc-full-sidcorr-1.sqlite.gz` is the same database, gzipped, at about one fifth
the size. Once decompressed it is byte-identical to the plain `.sqlite`, with the same
schema and the same contents, so nothing downstream needs to change beyond adding a
decompression step. The uncompressed file is still published alongside it for consumers who
would rather not.

### The features sidecar — 76 MB

`sidcorr-hvsc-full-features-1.jsonl.gz` is new, and it exists specifically for consumers
that want the raw feature records and nothing else. It contains no vectors and no
neighbours.

It is line-delimited JSON, gzipped, sorted by `track_id`, with one object per line:

```json
{"track_id": "DEMOS/0-9/Tune.sid#1", "sid_path": "DEMOS/0-9/Tune.sid", "song_index": 1, "features": {}}
```

The `features` object is the complete 129-key record, exactly as it appears in the
`features_json` column of the full export — same keys, same values, same feature schema
version. The format is JSONL rather than SQLite or Parquet so that reading it needs nothing
beyond gunzip and a JSON parser. It ships with its own manifest recording
`feature_schema_version`, `track_count`, `tracks_without_features`, `hvsc_version`, the
byte counts, and the digest of the SQLite export it was extracted from.

**When this is the right choice:** if your code extracts its own feature vector from
`features_json` and never touches `vector_json` or the `neighbors` table, then the lite
bundle — 8 MB, carrying track identity, paths and ratings — together with this sidecar
gives you the same inputs you have today. That is 84 MB against 982 MB, and it stays
proportionate as the vector and the neighbour graph grow in future releases.

## The `neighbors` table is no longer empty

This is the change most likely to alter behaviour without anyone changing any code, so it
is worth setting out fully.

In the 0.5-era export, `neighbor_row_count` was 0 and the `neighbors` table was empty. A
consumer written to use a precomputed neighbour cache when one exists, and to compute its
own ranking when it does not, would in practice always have taken the second path — the
first was never reachable with that data.

From 0.7.0 onward the table holds 25 rows per track. The same code will now take the first
path. Both are still available and both are reasonable; the difference is which ranking a
"more like this" query returns.

### What the stored ranking is

SIDFlow's neighbours are ranked by **weighted cosine similarity** over the 58-dimension
vector, using a table of 58 per-dimension weights fitted by coordinate ascent on nDCG@10.
The weights span 0.33 to 2.11, so they matter: they are not a mild adjustment to a plain
cosine.

Those weights are published in the manifest from 0.8.0 as `vector_weights`, alongside
`similarity_metric: "weighted-cosine"`. If you ever want to reproduce or extend the stored
ranking yourself, you need them — a plain cosine over the same vectors agrees with the
stored neighbours on roughly half of its results. The exact formula, including the detail
that the weight applies to the dot product *and* to both norms, is in the main guide and in
`doc/similarity-export.md`.

### If you import the table

You get SIDFlow's ranking. Two properties of the stored graph are worth knowing about in
advance:

**The depth is fixed at 25 per seed.** That is enough for a single "more like this" query,
but a feature that repeatedly draws further recommendations from the same seed — a radio
mode topping itself up, for example — will exhaust the stored set sooner than a
whole-corpus scan would, and will start repeating.

**Same-file siblings are common near the top.** HVSC files often contain several subsongs
of one tune, and those subsongs are frequently near-identical variants of each other. Across
the 2,196,700 stored rows, the rank-1 neighbour is a different subsong of the *same* `.sid`
file for **14.4%** of seeds, and 905 seeds have all 25 of their neighbours from their own
file. If that is not the result you want, excluding candidates whose `sid_path` matches the
seed's — rather than only excluding the seed's own `track_id` — removes them.

### If you do not import it

Your existing ranking stays in effect, exactly as it behaved against the 0.5-era export, and
the compact database is roughly 232 MB smaller.

## Manifest fields

The sidecar manifest gained three fields in 0.8.0 and clarified three more.

### New

**`hvsc_version`** records which HVSC release the export was built from, as a readable
string such as `"HVSC 85 + Update 85"`. Earlier releases recorded only
`corpus_version: "hvsc"`, which does not distinguish one HVSC from another. Since every
consumer resolves `sid_path` values against a local collection, this is the field that
tells you whether a path that failed to resolve is a missing file or simply a different
HVSC version — a distinction that previously had to be guessed.

**`similarity_metric`** names the metric the stored neighbours were ranked by:
`"weighted-cosine"` for the current 58-dimension vector, or `"cosine"` for the legacy
4-dimension one.

**`vector_weights`** is the 58-entry weight table itself, one number per dimension. It is
only present when the metric is `"weighted-cosine"`.

### Clarified

**`neighbor_row_count`** is now `SELECT COUNT(*) FROM neighbors`, measured from the
finished table. Previously it was computed as `track_count × neighbor_count_per_track`. The
two values coincide for every published HVSC export, so this changes nothing about the data
you have — but if your import validates the table against this field, it is now derived
from the table rather than from the intent of the run that produced it.

**`file_checksums.sqlite_sha256`** now matches the published file and agrees with
`SHA256SUMS`. For any release before 0.8.0, `SHA256SUMS` is the authoritative digest.

**`paths.sqlite` and `paths.manifest`** are basenames. Earlier releases may contain an
absolute path from the machine that built the export.

### One thing to check if you read the embedded copy

The manifest is published twice: as the `*.manifest.json` sidecar, and as a copy inside the
database's own `meta.manifest_json`. From 0.8.0 the embedded copy **omits `file_checksums`
entirely**, since a file cannot meaningfully contain its own digest. If you read the
embedded copy, treat that key as optional; the sidecar carries the digest.

## Feature coverage

Two keys, `spectralContrastMean` and `spectralContrastStd`, are absent from `features_json`
on approximately **0.14%** of tracks — 7 out of 5,000 sampled. Every other key used by known
consumers is present on every track.

This is worth a moment's thought if you z-normalise your feature dimensions corpus-wide.
Substituting `0.0` for a missing value in a z-normalised dimension does not place that track
at the centre of the distribution; it places it wherever `0.0` happens to fall, which for a
spectral-contrast measurement is some distance from the mean. At 0.14% the effect is small,
but it is a displacement rather than a neutral default.

No feature keys were removed between schema 1.3.0 and 1.5.0. 58 were added.

## Release naming

From 0.8.0, a `sidflow-data` release tag is simply the SIDFlow version that produced it —
this release is tagged `0.8.0`. Earlier releases used
`sidcorr-<corpus>-<profile>-<timestamp>`, which did not record the producing version
anywhere machine-readable.

Existing releases are **not** retagged. Every download URL published so far still resolves,
and `releases/latest/download/<name>` is unaffected by the change.
