# Migration addendum: the full SQLite export

An addendum to [Migrating from the 0.5-era data release to 0.8.0](./0.5-to-0.8.md), for
consumers of the **full** `sidcorr-1` SQLite export — `u64deck` in particular.

Everything in the main guide applies. This page covers what is specific to the full export.

---

## In short

Three things changed that a full-export consumer will notice.

1. **The file is bigger.** 416 MB → 982 MB, because it now carries a 58-dimension vector
   and 25 precomputed neighbours per track.
2. **There are two smaller alternatives.** A gzipped copy (194 MB), and a features-only
   sidecar (76 MB) that holds just the raw feature records.
3. **The `neighbors` table is no longer empty.** It was 0 rows; it is now 2.2 million.

Nothing was renamed or removed. All four original asset names still resolve.

---

## 1. Sizes

| | 0.5-era | 0.8.0 |
|---|---:|---:|
| full `.sqlite` | 416 MB | **982 MB** |
| full `.sqlite.gz` | — | **194 MB** *(new)* |
| features sidecar | — | **76 MB** *(new)* |
| lite bundle | 3.3 MB | 8.1 MB |

The growth is the vector and the neighbour graph:

- `vector_dimensions` went 4 → 58
- `neighbor_row_count` went 0 → 2,196,700 (25 per track)
- tracks went 87,073 → 87,868

**After import**, a compact database built with `slim_database()` holds 269.4 MB, against
37.6 MB from the 0.5-era export. Almost all of that difference is the imported `neighbors`
table — skipping it accounts for roughly 232 MB.

*(Both figures were measured by the July 2026 export audit, running `slim_database()`
against each export. 0.8.0 changed no track and no neighbour row from 0.7.0, so they apply
to both.)*

---

## 2. Two smaller assets

Both are new in 0.8.0, both are additive.

### `…-sidcorr-1.sqlite.gz` — 194 MB

The same database, gzipped. 5× smaller. Identical once decompressed. The plain `.sqlite`
is still published alongside it.

### `…-features-1.jsonl.gz` — 76 MB

Just the raw feature records — no vectors, no neighbours. One JSON object per line, sorted
by `track_id`:

```json
{"track_id": "DEMOS/0-9/Tune.sid#1", "sid_path": "DEMOS/0-9/Tune.sid", "song_index": 1, "features": {}}
```

`features` is the same complete 129-key record found in the `features_json` column. It
ships with its own manifest recording `feature_schema_version`, `track_count`,
`hvsc_version`, and the source SQLite's digest.

**Why this might matter:** if you read `features_json` but not `vector_json` or the
`neighbors` table, the lite bundle (8 MB, for track identity and ratings) plus this sidecar
gives you the same inputs in **84 MB instead of 982 MB**.

---

## 3. The `neighbors` table is populated

The 0.5-era export shipped it empty. From 0.7.0 it holds 25 rows per track, ranked by
weighted cosine over the 58-dimension vector.

If your code uses a precomputed neighbour cache when one is present and computes its own
ranking otherwise, it will now take the first path where it previously took the second.
Both remain available:

**If you import the table**, you get SIDFlow's neighbours. Two things to know:

- Depth is 25 per seed, so repeated draws from one seed exhaust it sooner than a
  whole-corpus scan would.
- For 14.4% of seeds the rank-1 neighbour is a different subsong of the *same* `.sid` file.
  905 seeds have all 25 neighbours from their own file. Excluding on `sid_path` rather than
  `track_id` filters those out.

**If you skip it**, your own ranking stays in effect and the compact database drops by
about 232 MB.

## 4. Manifest fields

New in 0.8.0:

| Field | What it is |
|---|---|
| `hvsc_version` | Which HVSC release the paths belong to, e.g. `"HVSC 85 + Update 85"`. Earlier releases only record `corpus_version: "hvsc"`. |
| `similarity_metric` | `"weighted-cosine"` for the 58-dimension vector. |
| `vector_weights` | One weight per dimension. **Needed to reproduce the stored `neighbors` ranking** — see the main guide. |

Changed in 0.8.0:

| Field | Before | From 0.8.0 |
|---|---|---|
| `neighbor_row_count` | `track_count × neighbor_count_per_track` | `SELECT COUNT(*) FROM neighbors`. The two match for every published HVSC export. |
| `file_checksums.sqlite_sha256` | use `SHA256SUMS` as the authoritative digest | matches the file, and agrees with `SHA256SUMS` |
| `paths.sqlite`, `paths.manifest` | may be an absolute path from the build host | basenames |

One more, if you read the manifest embedded in the database's `meta.manifest_json`: from
0.8.0 that copy omits `file_checksums` entirely. Treat the key as optional.

---

## 5. Feature coverage

`spectralContrastMean` and `spectralContrastStd` are missing on about **0.14%** of tracks
(7 of 5,000 sampled). Every other key used by known consumers is present.

Between `feature_schema_version` 1.3.0 and 1.5.0, **58 keys were added and none removed.**

---

## 6. Release naming

From 0.8.0 a `sidflow-data` release tag is the SIDFlow version that produced it — this one
is simply `0.8.0`.

Earlier releases keep their `sidcorr-<corpus>-<profile>-<timestamp>` tags. Nothing is
retagged, every existing download URL still resolves, and
`releases/latest/download/<name>` is unaffected.
