# Migrating from the 0.5-era data release to 0.8.0

**Audience:** anyone consuming a `sidflow-data` release published before 2026-07-26.

This is two hops, and they are different in kind. Work out which one affects you before
you read further:

| Hop | What changed | Who is affected |
|---|---|---|
| **0.5-era → 0.7.0** | **the data.** Vector, ratings, neighbours, corpus. | everyone. This is where the real behavioural break is. |
| **0.7.0 → 0.8.0** | **the contract.** Manifest fields, new assets, station membership, release naming. | small, but every item below needs a decision. |

If you are on `sidcorr-hvsc-full-20260726T203707Z` you only need the second half. If you
are on anything older, read both — and read the next section first, because it changes
how you should interpret any tuning you did against the old data.

Every number here was measured against the artefacts actually published, except where a
figure is explicitly attributed to the July 2026 export audit.

---

## Part 1 — 0.5-era → 0.7.0: the data changed

### What was broken in the 0.5-era release

This needs saying plainly, because a consumer who does not know cannot judge whether
their own tuning was compensating for it.

**The similarity data was inert.** Measured on `sidcorr-hvsc-full-20260407T115218Z`:

- **15 distinct vectors across 87,073 tracks.** 79,567 of them — **91.4%** — shared the
  literal vector `[3,3,3,3]`.
- **The ratings never took the values 1 or 5 at all.** `e` was 3 for 96% of the corpus,
  `m` for 94%, `c` for 94.6%.
- **`neighbor_row_count` was 0.** The "full" export shipped with no precomputed
  neighbours whatsoever.

The cause: `resolveTargetVectorDimensions()` returned 4 whenever no wider vector was
stored, which routed every track through the legacy `[e, m, c, p]` path. With the ratings
themselves collapsed onto 3, the vector became a constant.

**The consequences, stated without hedging:**

- **Vector-based recommendation was indistinguishable from random.** Not degraded —
  uninformative. Any "more like this" built on `vector_json` was returning arbitrary
  tracks.
- **Category selection was impossible.** 91% of the corpus sat in a single `(e,m,c)` cell,
  so no rating filter could partition anything.

If you tuned thresholds, weights, or diversity rules against that data, **those settings
are now wrong**. They were compensating for a degenerate distribution that no longer
exists. Re-tune rather than carry them over.

### What changed in the data

| | 0.5-era | 0.7.x / 0.8.0 |
|---|---|---|
| `vector_dimensions` | 4 | **58** |
| distinct vectors | 15 | 87,717 |
| `vector_normalisation` | *(absent)* | `rank-uniform` |
| `neighbor_row_count` | 0 | 2,196,700 (25 per track) |
| `feature_schema_version` | 1.3.0 | 1.5.0 (+58 keys, **none removed**) |
| `sid_engine` | *(absent)* | `sidlite` |
| tracks / files | 87,073 / 60,571 | 87,868 / 61,157 |
| full SQLite | 416 MB | 982 MB (194 MB gzipped) |
| lite | 3.29 MB | 8.12 MB |
| tiny | 1.82 MB | 1.83 MB |

The lite bundle grew 3.29 MB → 8.12 MB and bought a 14.5× wider vector. That is the whole
cost of the fix, and it is a good trade: 87,868 × 58 = 5.10 MB of quantised codes plus the
codebook.

### Breaking changes you must act on

1. **`vector_json` width changed 4 → 58.** Never hardcode it. Read `vector_dimensions`
   from the manifest. It is expected to grow again.

2. **Similarity is *weighted* cosine, not plain cosine.** This is the single most
   expensive thing to get wrong, and until 0.8.0 it was impossible to get right from the
   published specification — the weight table lived only in SIDFlow's TypeScript source.
   From 0.8.0 it is in the manifest as `vector_weights`, with `similarity_metric:
   "weighted-cosine"`.

   Measured over 3,000 seeds against the full export's stored neighbours:

   | What you compute | R@1 | R@25 |
   |---|---:|---:|
   | weighted cosine | **0.983** | **0.988** |
   | plain cosine | 0.478 | 0.505 |

   On a station grown from 5 favourites, top-50: **98%** agreement with the weights,
   **40%** without. Half your recommendations are different, and nothing about the result
   looks wrong.

   The weight applies to the dot product **and both norms** — equivalently, it is a plain
   cosine over vectors scaled component-wise by `√wᵢ`. Reweighting the dot product alone
   gives a different ranking. See `doc/similarity-export.md`.

3. **`e`/`m`/`c` are now meaningful, and rank-uniform.** They are exact corpus quintiles:
   17,574 / 17,573 / 17,574 / 17,573 / 17,574 for each, with all 125 `(e,m,c)` cells
   populated. Any threshold tuned against the old data — where 94%+ of tracks sat at 3 —
   is now wrong. Note also that `e=1` means "the calmest fifth of **this corpus**", not
   "objectively calm".

4. **The `neighbors` table is populated.** A consumer that prefers a precomputed cache
   when one exists, and computes its own ranking when it does not, will take a different
   path on this upgrade than it did on the 0.5-era export. See the
   [full-export addendum](./0.5-to-0.8-u64deck.md).

5. **209 track IDs present in the 0.5-era release are absent from 0.7+**; 1,004 are new.
   Handle missing seeds gracefully.

   **Cause established, no reclassification needed.** Of the 185 distinct files involved,
   **184 are entirely absent from HVSC 85 itself** — removed or renamed by HVSC between
   the release the 0.5-era export was built from and HVSC 85. Verified by resolving each
   path against a local HVSC 85 collection: zero of the 184 exist. The remaining case is
   `MUSICIANS/B/Bjerregaard_Johannes/Kamikaze.sid`, which went from 2 subsongs to 1
   because **HVSC 85's copy of the file declares `songs: 1`** in its PSID header.

   So this is not a SIDFlow coverage regression. It is the collection changing underneath
   two exports built ten weeks apart — which is precisely the ambiguity `hvsc_version`
   (new in 0.8.0) exists to remove.

6. **`file_checksums.sqlite_sha256` was wrong in every pre-0.8.0 release.** Verify against
   `SHA256SUMS`, which was always correct. From 0.8.0 both agree. See below.

## Part 2 — 0.7.0 → 0.8.0: the contract changed

No reclassification was run. The full export's *data* is bit-for-bit the same corpus;
what changed is its manifest, its station masks, and what else is published beside it.

### Every digest changes. Update your pins.

| Asset | Bytes | SHA-256 |
|---|---:|---|
| `sidcorr-hvsc-full-sidcorr-1.sqlite` | 982,155,264 | `d3d825ae0ed38139802b57cb7e8c2f01fc40bdbb824bf6669e9d2ef51bb176da` |
| `sidcorr-hvsc-full-sidcorr-1.sqlite.gz` **(new)** | 194,351,886 | `7eeddad82666fbf75ce93d0d412a7b31797475bee1b77c960542c7edb7b2fcf0` |
| `sidcorr-hvsc-full-sidcorr-lite-1.sidcorr` | 8,118,973 | `fe92bd57d7a3b53e5c5d398745002a81cdad50158ce7ffe82809d9e343a346cd` |
| `sidcorr-hvsc-full-sidcorr-tiny-1.sidcorr` | 1,834,993 | `64bee4464c89f605ea15e468168ff39b9f00bb8bf659da2af59ad0004f7c9c6d` |
| `sidcorr-hvsc-full-features-1.jsonl.gz` **(new)** | 75,933,721 | `006cd38804ee5289a28072f169d5dd0dd3b7d7c2ddb8e9369a8f2fbb5045f39b` |

Two things worth noticing in that table:

- **The lite bundle's bytes did not change at all.** `fe92bd57…a346cd` is the same digest
  0.7.0 published. Only its manifest gained fields. If you consume lite and do not read
  the manifest, 0.8.0 is a no-op for you — but you should read the manifest, because that
  is where `vector_weights` now lives.
- **The full export shrank**, 1,013,977,088 → 982,155,264 bytes. That is `VACUUM`
  reclaiming free pages during the manifest repair, not data loss: `track_count` is
  87,868 and `neighbor_row_count` is 2,196,700, unchanged.

### The manifest now describes the file

**`file_checksums.sqlite_sha256` has never matched the published file, in any release,
by construction.** The exporter hashed the database and then wrote the manifest —
including that hash — into the database's own `meta` table, mutating the bytes it had just
measured. The declared digest was the digest of a file that was never published.

| | 0.5-era | 0.7.0 | 0.8.0 |
|---|---|---|---|
| manifest `sqlite_sha256` | `510560e6…5d48` | `d7e5f77a…7d51` | `d3d825ae…76da` |
| actual file | `7eea82ef…4eb7f` | `17953aa5…c6d78` | `d3d825ae…76da` ✓ |
| `SHA256SUMS` | `7eea82ef…4eb7f` ✓ | `17953aa5…c6d78` ✓ | `d3d825ae…76da` ✓ |

`SHA256SUMS` was always right, so nothing downstream broke — but `sidflow-data` tells
consumers to "verify the checksum and retain the manifest", and a consumer who did that
rejected every release SIDFlow ever shipped.

**From 0.8.0:** the sidecar manifest carries the true digest, computed after the last
write. The copy embedded in the database's `meta.manifest_json` **omits `file_checksums`
entirely** — a file cannot contain its own digest, so it stops pretending it can. If you
read the embedded copy and expect that key, handle its absence.

### New manifest fields

| Field | Profiles | What it is |
|---|---|---|
| `hvsc_version` | full, lite, tiny | e.g. `"HVSC 85 + Update 85"`, or `"unknown"`. `corpus_version` was the bare string `"hvsc"` in every previous release, so nothing recorded which collection the paths belong to. |
| `similarity_metric` | full, lite | `"weighted-cosine"` or `"cosine"` |
| `vector_weights` | full, lite | one per dimension; **read this** |
| `style_populations` | tiny | persona key → track count, all nine |
| `style_population_policy` | tiny | the gate thresholds this build ran with |
| `style_population_waiver` | tiny | present **only** if the build bypassed a failing gate |

Two corrections rather than additions:

- **`neighbor_row_count` is now measured**, not `track_count × k`. The two happen to
  coincide for HVSC (2,196,700 = 87,868 × 25), so nothing changes here — but a future
  export where one seed cannot fill `k` will now report the truth instead of bricking any
  consumer that hard-fails on a mismatch.
- **`paths.*` are basenames.** The 0.7.0 full manifest published
  `/mnt/data/dev/c64/sidflow/data/exports/…`, the build host's absolute layout, in a file
  consumers are told to retain.

### Station membership changed for most of the corpus

If you use the tiny profile's style masks, **read this section**; if you do not, skip it.

The 0.7.0 masks were computed by taking each track's three highest-scoring personas
unconditionally. Measured on that bundle:

| Persona | 0.7.0 | % | 0.8.0 | % |
|---|---:|---:|---:|---:|
| `slow_ambient` | 46,652 | 53.1% | 17,574 | 20.0% |
| `nostalgic` | 45,562 | 51.9% | 17,574 | 20.0% |
| `melodic` | 45,496 | 51.8% | 17,574 | 20.0% |
| `experimental` | 42,495 | 48.4% | 17,574 | 20.0% |
| `fast_paced` | 41,648 | 47.4% | 17,574 | 20.0% |
| `era_explorer` | 29,116 | 33.1% | 17,574 | 20.0% |
| `deep_discovery` | 11,962 | 13.6% | 17,574 | 20.0% |
| `composer_focus` | 673 | **0.8%** | 17,574 | 20.0% |
| `theme_hunter` | **0** | **0.0%** | 17,574 | 20.0% |

- `theme_hunter` was a station that could never play anything.
- `composer_focus` looped after 673 tracks.
- The spread between largest and smallest non-empty station was **69×**; it is now **1.0**.
- **9,451 tracks carried both `fast_paced` and `slow_ambient`** — two stations a listener
  experiences as opposites. Now zero.
- 13,478 tracks (15.3%) carry **no** station at all, which the old forced-top-3 rule could
  not express. Do not assume every track has one.

**What is unchanged, deliberately:** all nine styles, their bit positions, their keys and
labels, `style_count = 9`, and `binary_format_version = 2`. The bit assignments are a wire
contract. Verified with `scripts/diff-tiny-sections.ts`: rebuilding the bundle changed
104,507 bytes of the style-mask table and **nothing else** — every `md5_48` identity, every
per-file subsong count, every packed rating and every neighbour record is byte-identical.

So a client that reads masks positionally gets corrected stations on a re-pin with no code
change. A client that has hardcoded population expectations needs to look again.

From 0.8.0 the export **fails the build** rather than shipping a starved or lopsided
station. Thresholds and measured results are in `style_population_policy` and
`style_populations`.

### Tiny's library reader (SIDFlow's own; not the format)

Two fixes that change what `@sidflow/common` returns. **The bundle bytes are not involved**,
so this affects you only if you use SIDFlow's TypeScript reader rather than your own.

- `openTinySimilarityDataset(...).info.hasVectorData` now reports **`false`**, and
  `getTrackVectors()` returns nothing. It previously reported `true` and synthesised
  `[e, m, c, p ?? 3]` — a 4-element rating vector with at most 125 distinct positions
  across 87,868 tracks. A consumer branching on the flag and doing centroid arithmetic
  silently reproduced the 0.5-era degeneracy.
- `recommendFromFavorites` now ranks from the neighbour graph. It previously computed a
  five-hop decayed walk and then **overwrote every score** with a cosine over that same
  4-element vector. Measured: a seed whose stored neighbours were `T6` @ 0.867 and `T7` @
  0.725 got them back 5th and 7th, behind two tracks that were not its neighbours at all,
  and all 11 returned scores matched an independent rating cosine to 12 decimal places
  while taking **5 distinct values**.
- Returned scores are now relative to the strongest match rather than clamped to 1.0. The
  walk accumulates, so raw scores exceed 1 and the old clamp reported the entire top 100
  as exactly `1.0`. The **ranking** was always correct; the number was not.

**Consequence to plan for:** a favourites query whose seeds have no neighbour edges now
returns **nothing**, rather than a corpus-wide ranking by a key known to be degenerate.

### New assets

Both additive. No existing filename changed: consumers resolve these names directly from
`releases/latest/download/`, so they are treated as a public API.

- **`sidcorr-hvsc-full-sidcorr-1.sqlite.gz`** — 194,351,886 bytes, **5.05×** smaller than
  the plain `.sqlite`, which stays alongside it.
- **`sidcorr-hvsc-full-features-1.jsonl.gz`** — 75,933,721 bytes. One JSON object per
  line, sorted by `track_id`: `{"track_id", "sid_path", "song_index", "features"}`, with
  its own manifest. This is the raw 129-key feature record without vectors and without
  neighbours.

**Which asset should you take?**

| You want | Take | Bytes |
|---|---|---:|
| recommendations, stations, similarity | **lite** | 8.1 MB |
| the same, on a very constrained client | tiny | 1.8 MB |
| to derive your own representation from raw features | lite + features sidecar | 84 MB |
| SQL access, or `features_json` in a database | full (prefer the `.gz`) | 194 MB → 982 MB |

**Lite is the right default for almost every consumer.** It reproduces the full export's
top-25 at R@25 = 0.9868 and its favourite-seeded stations at 98% overlap, in 0.8% of the
bytes. Full is for consumers that specifically need `features_json` or SQL.

### Release naming

From 0.8.0, **the `sidflow-data` release tag is the SIDFlow version that produced it**.

Historical releases are **not** retagged — their download URLs are live. The mapping:

| `sidflow-data` release | SIDFlow version | Published | Notes |
|---|---|---|---|
| `sidcorr-hvsc-full-20260315T095426Z` | pre-0.5.0 | 2026-03-15 | titled "0.5.0-rc1 (pre-tag build)"; predates tag `0.5.0-rc1` (2026-03-15 17:08 UTC) by seven hours |
| `sidcorr-hvsc-full-20260407T115218Z` | **0.5.6**, partly 0.5.7 | 2026-04-07 | see below |
| `sidcorr-hvsc-full-20260726T203707Z` | 0.7.0 | 2026-07-26 | |
| `0.8.0` | 0.8.0 | *this release* | |

**The 0.5-era row has a split lineage, and it is worth stating precisely.** The release
titles itself "SIDFlow 0.5.6" and its notes say `0.5.6`. Its full SQLite was generated
`2026-04-07T11:18:09Z`, when `0.5.6` (tagged 2026-03-30) was the newest tag. But its lite
and tiny bundles were generated the following morning, `2026-04-08T08:31:55Z` and
`08:32:12Z` — after `0.5.7` was tagged (2026-04-07 23:06 UTC). So the full export is a
0.5.6 artefact and the derived bundles are 0.5.7-era, in one release that names itself
0.5.6.

That ambiguity is exactly what the new scheme removes, and `release_tag()` now fails
loudly rather than generating a timestamp when it is not given a resolvable SIDFlow tag.

## `c64commander`

You consume the **tiny** export and are pinned to `sidcorr-hvsc-full-20260726T203707Z`.

1. **Ratings are meaningful for the first time.** On the 0.5-era data 94%+ of tracks sat
   at `e=m=c=3`, so every Style station drew from an essentially undifferentiated pool.
   Any tuning done against that is now wrong.

2. **Station membership changes for most of the corpus.** See the coverage table above.
   The two you will notice: **"Game Themes" goes from 0 tracks to 17,574**, and
   **"Fast-Paced" and "Chill / Ambient" no longer share 9,451 tracks**.

   Bit assignments, keys, labels and `style_count = 9` are unchanged, so **corrected masks
   reach users on a re-pin with no client change**.

3. **Read `style_populations` from the manifest.** It is the machine-readable source for
   tile counts, and it means you do not need a full pass over the mask table to render
   them. Recommended, and being done on the client side in parallel with this release:
   hide or disable a tile whose population is zero, and show the count on each tile.

4. **From 0.8.0 the export fails rather than shipping a starved station.** If a future
   bundle carries `style_population_waiver`, it was built under an explicit bypass — treat
   that as a signal, not as normal.

5. **Tiny still carries no vectors**, and its bundle shape is unchanged in 0.8.0. Its
   retrieval model is a decayed walk over the 3-neighbour graph, not vector search. Worth
   restating so the client does not expect otherwise.

   The `hasVectorData` and `recommendFromFavorites` fixes above are in SIDFlow's own
   **library** reader. `c64commander` has no dependency on `@sidflow/common` and reads the
   bundle with its own `sidcorrTiny.ts`, so **it was never affected** — this is a library
   note, not a re-pin action.

## Verifying what you downloaded

```bash
sha256sum -c SHA256SUMS
```

`SHA256SUMS` and the sidecar manifests agree from 0.8.0. If you want to check the whole
release the way SIDFlow's own gate does:

```bash
bun run verify:exports -- --exports <download-dir> --hvsc <your-hvsc>
```

And if you have implemented the lite format yourself, this checks your metric against the
authoritative neighbours:

```bash
bun run verify:lite-against-full -- \
  --lite <download-dir>/sidcorr-hvsc-full-sidcorr-lite-1.sidcorr \
  --full <download-dir>/sidcorr-hvsc-full-sidcorr-1.sqlite --seeds 1000
```
