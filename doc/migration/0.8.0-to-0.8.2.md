# Migrating from `sidflow-data` 0.8.0 to 0.8.2

One artefact changed: the tiny bundle's neighbour table and the `graph_flags` field in its header.
Everything else in the release carries the byte-for-byte contents it had in 0.8.0, which the
checksums below show directly.

> **A note on 0.8.2's history.** A release tagged 0.8.2 existed briefly and was **withdrawn** — its
> releases and tags were deleted from both `chrisgleissner/sidflow` and
> `chrisgleissner/sidflow-data`. It shipped one definition of what a tiny neighbour edge means; this
> release ships a different one. Publishing both would have asked every consumer to absorb two
> incompatible redefinitions of the same field within days, for no benefit, since nobody had built
> against the first. The number is therefore reused, and a consumer's history reads 0.8.0 → 0.8.2
> with a single change in what the edges mean.
>
> If you fetched the withdrawn 0.8.2 tiny bundle (`62097331…c62d294`), discard it. It is not the
> bundle described here.

## What changed

`sidcorr-hvsc-full-sidcorr-tiny-1.sidcorr` — the neighbour table and `graph_flags`. Nothing else in
the bundle: every `md5_48` file identity, per-file track count, style mask and packed rating is
unchanged, so station membership is identical and every style tile keeps its population.

**The exported graph is now a proximity index and nothing else.** Two guarantees were withdrawn:

1. **Acyclicity.** `graph_flags` bit 0 read 1 in 0.8.0 and the specification called it "always 1".
   It now reads **0**, and acyclicity is no longer claimed or true. The guarantee expressed a
   playback policy — never play the same tune twice — as a constraint on which true similarity
   relationships the export was allowed to state, and enforcing it discarded **50.76%** of the
   source export's edges. Not revisiting a track is the player's job, and every player already keeps
   a set of what it has played.
2. **The ordinal rule.** 0.8.0 required every target to be a track ordinal strictly smaller than the
   seed's. That is gone; a target may have any ordinal.

What replaces them: edges chosen by Vamana (DiskANN) construction with diversifying pruning, reverse
insertion, a reachability repair and a bound on in-degree. Concretely, against 0.8.0:

| | 0.8.0 | 0.8.2 |
|---|---:|---:|
| mean out-degree | 2.799 of 3 | **3.000 of 3** |
| tracks with no incoming edge | 24,669 (28.08%) | **0** |
| tracks with no outgoing edge | 2,786 | **0** |
| largest undirected component | 99.08% | see release notes |
| rows in descending similarity order | 100% | 100% |
| greedy routing recall@1 | 0.30% | see release notes |

Row order is descending similarity, so slot 0 is the seed's closest exported neighbour — the same
convention 0.8.0 used. `doc/similarity-export-tiny.md` §10.3–§10.5 is the normative statement, and
`doc/neighbour-graph-design.md` records the construction, the parameter sweeps that chose its
settings, and the two designs that were rejected with their measurements.

## What each consumer needs to do

**A reader that only parses the format needs no change.** `binary_format_version` is still `2`, the
header layout and section order are unchanged, and the neighbour table has the same shape.

**A reader that validated either withdrawn guarantee must drop the check.** Specifically:

- A reader that rejected a bundle whose targets were not lower track ordinals will reject this one.
- A reader that asserted acyclicity, or that relied on it to bound a traversal, will now find
  cycles. This is the change that matters most, and it is deliberate. If your traversal terminated
  *because* the graph was acyclic, it will not terminate now: keep a visited set instead. This is
  the correct implementation in any case — a similarity graph that is prevented from stating that
  two tracks are each other's nearest neighbour is a worse index, not a safer one.
- `graph_flags` bit 3, which the withdrawn 0.8.2 used to declare a flow successor in slot 0, is
  retired and never set. §5.2 already required consumers to ignore bits they do not recognise.

**`c64commander`** pins the tiny bundle by tag and digest in `src/lib/sidRadio/sidcorrRelease.ts`,
with a second copy in `scripts/fetch-sidcorr.mjs` that a test asserts never drifts. It is pinned to
**0.8.0**, so it was never exposed to the withdrawn 0.8.2. Re-pinning needs both constants updated.
What re-pinning does and does not buy:

- Station membership is unchanged, because the style masks are byte-identical.
- Station *length* improves substantially from the data alone, but not to the point the product
  needs. The engine expands at most 8 hops from a seed that never moves, so it is bounded by its hop
  budget rather than by the graph. Reaching a station that runs for hours needs the client to let
  its query drift with what the listener has heard; that ships alongside this release and is
  described in `doc/neighbour-graph-design.md` §7.
- Deduplication at the tune level rather than the track level is a client change too: the exclusion
  set holds track ordinals, so a station will otherwise play three subsongs of one `.sid` file in a
  row. `md5_48` is the file identity and the bundle already exposes every sibling of a track.

**`u64deck`** consumes the full export and is unaffected. `sidcorr-hvsc-full-sidcorr-1.sqlite`, its
`.gz`, its manifest and the features sidecar are the same bytes as in 0.8.0, so its `neighbors`
import, its slimmed database and its "♪ More like this" results are all identical. The asset
filenames are unchanged, so `releases/latest/download/<name>` keeps resolving.

**Third parties building their own index from the full export.** The full export's 25-neighbour
table is a retrieval answer and was deliberately left as it is; see the 0.8.2 entry in `CHANGES.md`
for that decision and the measurements behind it. If you are building a small-degree graph of your
own from it, `doc/neighbour-graph-design.md` §3 is worth reading first: selecting three of the 25
nearest neighbours cannot produce a searchable graph, because all 25 sit in a narrow shell around
the seed and none of them crosses the space.
